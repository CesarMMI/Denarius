# Progress Log

## Estado atual do projeto

O backend está funcionalmente completo: todas as 18 features de domínio estão implementadas, expostas via Minimal API e cobertas por testes nas quatro camadas (368 testes, 0 falhas). CORS foi adicionado como feature de infraestrutura. A partir desta sessão, o projeto também está containerizado: `docker compose up` de dentro de `api/` sobe a API + MariaDB, com migrations aplicadas automaticamente. Não existe compose na raiz do repositório — cada projeto do monorepo (api, e futuramente front) tem seu próprio `docker-compose.yml`/`docker-compose.override.yml` totalmente independente, e é executado separadamente (nunca combinados em um único comando). O projeto encontra-se em estado pronto para integração com um cliente (front-end ou mobile).

Prod: `docker compose -f docker-compose.yml up` (só o base, sem override) — sempre de dentro de `api/`. Quando o `front/` for dockerizado, segue o mesmo padrão: compose próprio, executado separadamente
- Testado de ponta a ponta várias vezes: build, migrations, `register`/`login` via curl, persistência de dados entre `down`/`up`, e a diferença de config dev vs. prod via `docker compose config`
- `dotnet build` e `dotnet test` confirmados passando (368 testes) após a alteração em `Program.cs`
- Docker agora é o único jeito de rodar a API — removidos `run-api.ps1` (raiz) e `api/src/Denarius.Api/appsettings.Development.json` (não tinham mais efeito: o primeiro chamava `dotnet run` local, o segundo era excluído da imagem via `.dockerignore` e já seria sobrescrito por env vars mesmo se existisse). `api/CLAUDE.md` atualizado: "Rodar localmente" agora documenta `docker compose up`; "Migrations (EF Core)" documenta como gerar novas migrations localmente via `dotnet ef migrations add` passando `ConnectionStrings__DefaultConnection` por env var (já que não há mais `appsettings.Development.json`), apontando para o MariaDB exposto em `localhost:3306` pelo `docker-compose.override.yml`; seção 5 (regras) atualizada para referenciar `api/.env.example` no lugar do arquivo removido
- `api/init.ps1` corrigido e fortalecido: (1) salvo como UTF-8 com BOM — sem BOM, o PowerShell 5.1 interpretava mal o travessão do banner e quebrava o parser (`AmpersandNotAllowed`), bug pré-existente sem relação com Docker; (2) Passo 4 ("verificação de inicialização") reescrito de `dotnet run --project src/Denarius.Api --no-build` + esperar 10s (não bloqueante, e que agora sempre "passava" mesmo sem nenhum banco configurado, já que a criação do `DbContext` é lazy — só falha se uma requisição real tocar o banco) para um check real via Docker: `docker compose build` → `up -d` → espera `mariadb` ficar `healthy` (via `docker inspect --format='{{.State.Health.Status}}'`, timeout 60s) → `POST /api/auth/register` de verdade (timeout 30s, espera 201) → `docker compose down -v` sempre ao final (sucesso ou falha, via função `FailDocker`), garantindo que o passo realmente exercite migrations + conexão com o banco, e que nunca deixe containers/volumes órfãos. Também descoberto e corrigido: `$ErrorActionPreference = "Stop"` + qualquer redirecionamento de stderr (`2>&1`, `*>`) em cima de comandos nativos (`docker`, `dotnet`) no PowerShell 5.1 vira `NativeCommandError` e aborta o script mesmo em sucesso — os comandos Docker agora rodam sem redirecionar stderr, só capturando stdout quando necessário (`| Out-Null`, atribuição de variável)
- **Simplificação do compose (a pedido do usuário):** removido o `docker-compose.yml` da raiz (que usava `include:`); `docker-compose.override.yml` movido para `api/docker-compose.override.yml`. Agora cada projeto do monorepo roda seu compose de forma totalmente independente, de dentro da própria pasta (`cd api && docker compose up`). `init.ps1` ajustado (removida a `Push-Location` até a raiz — roda direto em `$PSScriptRoot`, que já é `api/`). `CLAUDE.md` e `feature_list.json` atualizados para remover as referências ao `include:`/raiz.
- **`Logging`, `Cors` movidos para env var (exceto `AllowedHosts`, mantido só em `appsettings.json`):** `AddCorsPolicy` (`Extensions/ServiceCollectionExtensions.cs`) mudou de `GetSection(...).Get<string[]>()` (array JSON indexado) para `configuration["Cors:AllowedOrigins"]` + `Split(',')` manual — necessário porque variáveis de ambiente não representam bem arrays indexados (`__0`, `__1`, ...) num `.env` plano. `appsettings.json` atualizado de arrays vazios (`[]`) para strings vazias (`""`) nas três chaves de `Cors`, mantendo o mesmo comportamento (`AllowAny*` quando vazio). Novas env vars em `api/docker-compose.yml`/`api/.env.example`: `LOGGING_DEFAULT_LEVEL`, `LOGGING_ASPNETCORE_LEVEL`, `CORS_ALLOWED_ORIGINS`, `CORS_ALLOWED_METHODS`, `CORS_ALLOWED_HEADERS`. Testado via `docker compose` real com origens/métodos/headers customizados: preflight OPTIONS confirmou os headers `Access-Control-*` corretos pra origem permitida e nenhum header CORS pra origem não listada. `dotnet build`/`dotnet test` (368 testes) confirmados passando após a mudança — os testes de CORS (`CorsTests.cs`) usam `FixedCorsPolicyProvider` e não exercitam `AddCorsPolicy` diretamente, então não foram afetados.
